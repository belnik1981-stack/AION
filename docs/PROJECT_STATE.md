## 1. Назначение этого файла

Этот файл — компактная проектная память AION. Он хранит только актуальное состояние, устойчивые архитектурные решения, подтверждённые факты, открытые вопросы и ближайший рациональный шаг.

Полная переписка чата сюда не копируется. Повторы, промежуточные рассуждения и отменённые идеи не сохраняются как текущее состояние. Предыдущие версии этого файла сохраняются историей Git.

Метки:

- **FACT** — подтверждено кодом, тестом, CI или первичным артефактом.
- **DECISION** — принятое архитектурное решение.
- **HYPOTHESIS** — рабочая гипотеза, требующая проверки.
- **OPEN** — ещё не реализовано или не доказано.
- **UNKNOWN** — данных недостаточно.

Нельзя превращать `HYPOTHESIS`, `OPEN` или текст модели в `FACT` без проверки.

## 2. Цель текущего этапа

AION развивается как truth-controlled система, в которой модели не определяют истину голосованием. Их ответы рассматриваются как утверждения, которые должны сопоставляться с происхождением данных, независимостью источников, противоречиями и доступными доказательствами.

Текущая минимальная архитектура:

```text
EVIDENCE / PROVENANCE
        ↓
CLEAN / COMPARE
        ↓
MULTI-MODEL ANALYSIS
        ↓
FINAL SYNTHESIS WITH UNCERTAINTY
```

**DECISION:** не создавать новый слой, если необходимая функция уже существует и может быть расширена без нарушения своей роли.

**DECISION:** простота, проверяемость и вычислительная доступность имеют преимущество перед архитектурным усложнением при одинаковом качестве результата.

## 4. Мультимодельный режим

**FACT:** текущая экспериментальная ветка поддерживает `AION_MODELS=model1,model2,...`.

При двух и более моделях Pipeline:

1. получает независимые исходные ответы моделей;
2. сохраняет их отдельно;
3. ротирует роли Planner / Analyst / Critic / Synthesizer / Verifier;
4. сохраняет назначение ролей и результаты раундов;
5. использует валидированные Evidence Objects v2, если задан `AION_EVIDENCE_BUNDLE`.

**DECISION:** мультимодельное согласие не является доказательством истины само по себе.

**DECISION:** общий информационный предок нескольких моделей или источников не должен считаться несколькими независимыми подтверждениями.

**OPEN:** текущие claim extraction, polarity и matching детерминированы, но
эвристичны; полноценная semantic verification и внешняя проверка URL не выполнены.

## 5. Рациональное использование вычислений

**DECISION:** вычислительная нагрузка должна расти вместе с неопределённостью и риском задачи, а не с количеством архитектурных компонентов.

Предпочтительный порядок:

```text
нормализация / dedup / dependency roots
        ↓
простая проверка противоречий
        ↓
1 модель, если этого достаточно
        ↓
2+ модели только при существенной неопределённости
        ↓
role rotation только при необходимости
        ↓
дополнительная evidence verification для нерешённых конфликтов
```

Цель: минимально необходимое число API-вызовов, токенов и повторных раундов при сохранении проверяемости результата.

## 6. Принципы AION — отдельный контур

Текущие принципы из `knowledge/truth/truth.json`:

1. Не выдавать гипотезы за факты.
2. Сохранять неопределённость там, где она существует.
3. Проверять значимые утверждения.
4. Безопасность имеет приоритет над автономностью.

**DECISION:** принципы проверяются только относительно других принципов: совместимость, согласование, пересечение, дублирование, напряжение, противоречие.

Правила исполнения, лимиты, роли, API, фильтры, memory, evidence mechanics и другие составляющие проекта не смешиваются с проверкой принципов.

**FACT:** между четырьмя текущими принципами прямого противоречия не выявлено.

## 7. Информационное и стимулированное искажение

**DECISION:** коммерческий интерес не является доказательством ложности данных и не является критерием истины.

**DECISION:** итог AION не должен изменяться ради коммерческой, финансовой, репутационной или институциональной выгоды стороны.

**HYPOTHESIS:** экономические и другие стимулы могут систематически влиять не только на формулировку данных, но и на их создание, отбор, публикацию, задержку раскрытия или сокрытие неблагоприятной информации.

**DECISION:** коммерческая зависимость анализируется отдельным параллельным
view и не изменяет основной доверенный pipeline. Введённые пользователем
коэффициенты остаются непроверенной гипотезой, а не доказательством причинности.

**DECISION:** для дальнейшей доказательной проверки предпочтительно расширять
существующее описание provenance/dependency root минимальными признаками,
например:

- `incentive_type`;
- `incentive_strength`;
- `data_control`;
- `suppression_risk`.

**OPEN:** эти поля и их проверка ещё не внедрены в Evidence Objects v2.

**DECISION:** отсутствие опубликованных негативных данных не должно автоматически трактоваться как отсутствие риска, если существует существенный стимул и возможность контролировать раскрытие информации.

## 8. Параллельные версии реальности

**DECISION:** противоречащая версия не должна уничтожать исходные доказательства или историю предыдущего состояния знания.

AION должен сохранять происхождение утверждения, его версии и причины изменения статуса, чтобы различать:

- исходные наблюдения / первичные evidence;
- производные интерпретации;
- повторения общего информационного предка;
- конкурирующие claims;
- позднее опровержение или подтверждение.

**DECISION:** уже подтверждённое утверждение не должно автоматически переоткрываться из-за нового мнения модели; нужен новый существенный evidence или установленный дефект предыдущей проверки.

**OPEN:** формальный runtime-механизм такого reopen ещё не реализован.

**FACT:** multi-model runtime строит отдельный claim registry с типами,

**FACT:** runtime формирует отдельное сравнение claim influence с коммерческим

**FACT:** evidence collector вручную проверяет каждый redirect, блокирует
non-global адреса, нестандартные порты и HTTPS downgrade, ограничивает ресурсы

**FACT:** optional Agents SDK runtime по умолчанию допускает только free-модели
OpenRouter, отключает SDK retries, ограничивает turns/tokens/model-call и весь

memory.

**FACT:** успешные negative-control сценарии больше не оставляют ложные
верхнеуровневые строки `[FAIL]` в полном журнале; PR #30 прошёл пять workflows,

**FACT:** PR #31 не позволяет caller-selected policy ослабить long-term
promotion, полностью пересчитывает derived verification metadata, учитывает

**FACT:** PR #32 запрещает обучение по голым
`score/verdict`, заново проверяет структурированный verification record,
исключает self/model corroboration, блокирует replay и атомарно сохраняет
состояние с восстанавливаемой pending audit-очередью. Пять workflows, Python
3.10/3.12, Agents SDK contract и повторный post-merge offline trial прошли.

**FACT:** текущий этап переводит stateful monitor коммерческого параллельного
слоя на блокируемые атомарные транзакции и восстанавливаемую pending
audit-очередь. Секреты, нефинитные числа и повреждённая структура блокируются;
лимиты случаев, истории, pending events и размера state не удаляют старые
данные, а останавливают новую запись.

**FACT:** текущий этап закрывает обход analysis-only bridge: claim registry
больше не принимает произвольный список как валидированный evidence. Контекст
содержит детерминированный digest и процесс-локальный HMAC seal, повторно
проверяется до первого provider call и не раскрывает локальный путь bundle.
Изменение claim или флага полномочий блокирует весь evidence-контекст.

## 10. Открытые технические ограничения

- **FACT:** основной pipeline использует единый call budget; повтор после
  усечения расходует его как отдельный вызов.
- **FACT:** provider timeout ограничен оставшимся `timeout_seconds` общего
  монотонного deadline.
- **OPEN:** нет доверенного внешнего механизма проверки реальной независимости скрытых dependency roots.
- **OPEN:** значения коммерческих факторов пока задаются пользователем и не
  подтверждаются независимыми источниками; их причинная связь не доказана.
- **OPEN:** внешняя подлинность provenance и semantic truth verification остаются нерешёнными.
- **OPEN:** DNS/IP guard не даёт абсолютной защиты от DNS rebinding между
  проверкой адреса и системным соединением.
- **OPEN:** автоматическое promotion в long-term memory/Truth не разрешено.
- **FACT:** response-size cap применяется до JSON parsing.
- **FACT:** Agents SDK использует отдельный bounded budget из тех же Truth
  limits; одновременный SDK run и основной pipeline пока не делят один счётчик.
- **OPEN:** принудительная отмена уже начатого системного вызова остаётся
  best-effort поверх socket timeout.
- **OPEN:** pattern redaction не гарантирует обнаружение неизвестных форматов
  чувствительных данных; шифрование at rest не реализовано.
- **OPEN:** ограничение роста episodic history должно сохранять архив, а не
  удалять старые записи.
- **OPEN:** человеческий reviewer и заявленные evidence attributes не доказывают
  внешнюю подлинность источника; promotion не означает Truth update.
- **OPEN:** даже целостный verification record не доказывает внешнюю подлинность
  `source_type` и `independent_group`; adaptive learning поэтому остаётся
  ограниченной калибровкой, а не доказательством истины.
- **OPEN:** защищённое хранение commercial monitor не подтверждает причинную
  коммерческую зависимость; оно сохраняет только состояние параллельной
  гипотезы и наблюдаемого сравнения.
- **OPEN:** process-local seal подтверждает только неизменность контекста между
  bridge и registry в одном процессе; он не доказывает внешнюю подлинность
  bundle, источника или его владельца и не предназначен для долговременной
  подписи.

## 11. Ближайший рациональный шаг

Не создавать новый большой слой.

После завершения integrity-bound evidence context следующий подтверждённый
разрыв — преобразовать безопасно полученный внешний документ в карантинный
RawArtifact/EvidenceObject draft без автоматического допуска в claim registry.
Сетевой fetch, извлечение текста, provenance, смысловая связь с claim и внешняя
проверка должны оставаться разными этапами.

После этого отдельно оценить необходимость:

1. semantic claim extraction / matching;
2. независимо проверяемых признаков incentive distortion;
3. adaptive escalation по вычислительной нагрузке;
4. reopen только по существенному новому evidence.

Каждый новый механизм сначала проверяется на совпадение с уже существующим кодом и архитектурой.
